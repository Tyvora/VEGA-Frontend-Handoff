# Scientific source → frontend traceability

All ten algorithm modules currently contain scaffolding, not executed algorithms. Expected outputs below are presentation requirements for their future producers, not existing results. `data.scientific_products[]` is a typed shared reference record: algorithm/product_type pair, result_id, method/version, product/observation IDs, optional asset, measurements, positions, related IDs, uncertainty/validation and provenance. It is always an array (empty today). Large tables/maps use an Asset reference rather than embedding unlimited data. It does not impose internal function names.

Field paths are relative to each view's response data except where explicitly prefixed. Shared Measurement records carry quantity name/unit/method/version/value/uncertainty; null is not zero. For a large typed table referenced by asset, the service must publish the table's schema version before a frontend consumes rows. In version1.0 the browser can display the summary and offer a link; arbitrary unversioned table content is never automatically rendered as measurements. This is an intentional boundary: engine result formats are not invented in this presentation task.

Prepared data are upstream prerequisites, not any of these outputs. Existing sky_visualization metadata/arrays provide target/product/observation, native shape, unit, WCS and masks. Existing readiness fields map directly to data_readiness, retaining original decisions. The planned formatter converts source unit spelling to canonical display tokens without changing numeric values, maps paths to opaque authorized references, and populates only actual outputs. It is not implemented here. Candidate synthetic fixtures cannot be traced to NASA observations and are labeled accordingly.
